## 1. 锁定的技术栈

| 层 | 选型 |
|---|---|
| 后端 | **.NET 8**（ASP.NET Core / C#） |
| 存储 / 缓存 / 消息 | **MySQL + Redis + RabbitMQ** |
| 前端 | **Vue + Element Plus** |
| **范围外** | **企业微信 / 任何外部 IM 集成（用户已移除）** |

用户明确指定 .NET 8。已知风险：.NET 8 官方支持于 **2026-11-10 结束**（2026-11-06 核实）。本地运行、CI、作品集演示均不受影响；若后续上线公网 demo 或宣称生产可用，再评估平滑升级 .NET 10。**此项不改动用户决定**。

**企业微信已移除**：项目变为完全自包含、零外部依赖，`docker compose up` 即可演示全部功能。定时能力本身不丢——超时关单仍用 RabbitMQ 延迟消息，每日日报改为 Quartz 定时生成的站内对账报表（落 MySQL、后台可查），异常告警改为后台告警页。去掉外部集成后，作品集反而更聚焦、演示更可靠。

Element Plus 要求 Vue 3；Vue 小版本不锁死，实施前复核。

## 2. 栈对产品形态的约束

Element Plus 是**中后台组件库**（表格、表单、弹窗、复杂筛选、状态标签、菜单权限），不是可视化大屏组件库。因此：

- 产品主体应是**管理后台型业务系统**，实时性 / 图表退为后台中的一个监控页。
- 上一轮首推的「实时事件处理管道 + 可视化大屏」**降级**：其门面是 ECharts 图表，Element Plus 无处安放，前端栈与产品形态割裂，全栈作品集里前端会变成摆设。
- 全栈项目要让 Element Plus 真正用满：复杂表格、状态流转、批量操作、对账筛选、人工补偿台。

## 3. 作品集选型标准

1. 业务零解释成本，面试官不用先听背景。
2. Redis / RabbitMQ / MySQL 各自对应一个能讲五分钟的真实问题，禁止为凑栈而堆。
3. 能用实验量化：压测、故障注入、对账一致。
4. 前端栈用得满，不是静态壳子。
5. `docker compose` 一键启动，README 首页放演示 GIF（沿用既定交付偏好）。

## 4. 候选方案对比（待用户拍板）

| 方向 | 强项 | 弱项 |
|---|---|---|
| **A. 订单履约 / 交易中台（首推）** | 业务零解释成本；三个中间件都是刚需；Element Plus 用得最满；零外部依赖、项目自包含；每个技术点可量化 | 题材烂大街，差异化必须靠工程证据而非业务花样 |
| **B. 分布式任务调度 / 批处理中心** | 三个中间件角色最正统；执行实例表格、实时日志、重试记录天然适配 Element Plus；定时任务成为平台核心能力而非外挂 | 偏基础设施，非技术面试官看不懂价值；会被问「为什么不用 Hangfire / Quartz」 |
| **C. 工单 / SLA 流转系统** | 业务最易懂，Element Plus 适配度最高；超时催办与 SLA 升级是天然业务功能 | 技术深度偏浅，Redis / MQ 容易显得硬塞 |
| **D. 实时事件大屏**（上一轮首推） | 视觉冲击最强 | 与 Element Plus 割裂，已降级；草案存 `docs/archive/realtime-dashboard-draft.md` |

## 5. 首推方案 A 的技术落点（讨论用，未定稿）

后台页面：商品与库存、订单列表（多条件筛选 + 状态流转）、发货与售后、对账报表、死信人工补偿台、实验台、系统告警页。

链路：下单 → MySQL 事务落订单 + outbox → RabbitMQ 异步履约（扣库存 / 生成单据）→ 超时未支付自动关单 → 失败进死信并人工补偿。异常与日报均留在站内。

| 组件 | 非它不可的理由 | 可复现实验 |
|---|---|---|
| MySQL | 订单 / 库存 / 流水状态机 + outbox 同事务 | 停掉 MQ，重启后消息不丢 |
| Redis | 库存预扣、幂等 token、分布式锁、热点缓存 | 并发下单超卖率 0 |
| RabbitMQ | 异步履约、超时关单（延迟消息的正当场景）、重试死信、削峰 | 重复投递 1000 条，库存不重复扣 |
| Vue + Element Plus | 订单表格、状态标签、批量发货、对账筛选、死信补偿 | 完整全栈演示 |

差异化策略：不做「一个秒杀接口」，做**完整履约链路 + 消息可靠性闭环**（outbox → 至少一次投递 → 幂等消费 → 死信补偿）+ 三个实验的实测数据。业务普通、证据硬，比堆业务花样更可信。

## 6. 最终成品形态

### 6.1 打开是什么

- **用户端（极简）**：商品列表 → 购物车 → 下单 → 模拟支付结果页。只为让链路有入口，不做营销页。
- **Element Plus 运营后台**：仪表盘、商品与库存、订单列表（多条件筛选 + 状态标签 + 批量操作）、发货与售后、对账报表、死信补偿台、系统告警页、实验台。
- **演示数据**：种子数据（数百 SKU、数千订单）+ 一键流量生成器，不是空表 demo。

### 6.2 30 秒演示脚本（README 首页 GIF）

下单 → 待支付 → 支付成功 → 库存由预扣转实扣 → 后台订单状态实时跳转 → 另一单超时未支付自动关单且库存回滚 → 注入一条履约失败 → 死信补偿台人工重试成功。

### 6.3 拿得出手的证据

三个可复现实验及数据表（停 MQ 不丢消息 / 重复投递不重复扣 / 并发下单零超卖）、压测报告（吞吐、P99、恢复耗时）、架构图、测试通过记录与红绿 TDD 的提交历史、README 第一屏。

### 6.4 明确不做（防范围膨胀）

真实支付、营销 / 优惠券 / 秒杀活动、多商户、物流对接、App / 小程序、外部 IM 集成、完整权限体系（仅一个演示账号）。

## 7. 能否作为正式系统上线

分三档，结论完全不同：

| 上线含义 | 结论 | 说明 |
|---|---|---|
| **作品集演示站**（公网可访问，全模拟数据） | **能，且强烈建议** | 一台小机器 + 域名 + `docker compose`；首页明确标注「演示环境、非真实交易」 |
| **内测 / 熟人小店记单**（不收钱、不存真实个人信息） | 勉强能，需先补齐 | 认证授权、备份恢复、监控告警、日志留存、数据导出 |
| **对外经营、真实收款发货** | **不能，也不建议** | 见 7.1 |

### 7.1 拦住它的主要不是技术

- **支付资质**：微信支付 / 支付宝商户号需要企业营业执照与已备案域名，个人主体拿不到。
- **合规**：ICP 备案；电子商务法下的经营者登记、商品信息披露、交易记录保存不少于三年；个人信息保护法下的手机号与收货地址；发票与售后责任。
- **运维责任**：真实订单丢失就是事故。当前设计是单实例 MySQL / Redis / RabbitMQ，没有高可用、备份恢复与灾备。
- **安全**：金额篡改、支付回调伪造、重放、越权、敏感数据加密，均不在作品集范围内。
- **框架**：.NET 8 于 2026-11-10 EOL，生产使用本身就是安全与合规问题。

一句话：**卡住的不是 Redis / RabbitMQ 学得好不好，是资质、合规和运维责任**。

### 7.2 建议

1. 把目标锁定为「**可公网访问的作品集演示站 + 一份写清楚的边界说明**」。能讲清「为什么这不是生产系统、要上线还差什么」，比含糊说「可以上线」更专业、更加分。
2. 若要体验部署全流程，就做成纯模拟经营沙盘：虚构 SKU、无真实用户、无支付、数据可随时清空，公网部署没有合规负担。
3. 「上线」作为可选里程碑 M7，等核心链路与实验数据完成后再做，且只做演示站。
4. 性价比判断：做到演示站已是作品集收益的最高点；再往上（高可用、等保、支付资质）对求职展示几乎零收益，成本却是数量级的。
